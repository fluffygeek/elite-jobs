# Pessimistic whole-Job locking for Office Staff edits

Issue #1's original concurrency design (implemented across issues #7, #8, #24, #25) made every Job field its own compare-and-swap "field group of one": a save was always a targeted `UPDATE ... WHERE id = ? AND field = expectedOldValue`, rejected with "this changed, reload" when the old value no longer matched. Two staff editing *different* fields on the same Job never contended at all, and a same-field collision was caught rather than silently overwritten.

In practice this asked Office Staff to reason about a fine-grained conflict model — edit whatever you want, find out after the fact whether someone else touched the exact same field first — for a workflow that's really just "one person corrects one Job at a time." Staff wanted a simpler mental model: open a Job, it's yours to edit, save or cancel when you're done. That's pessimistic locking, not optimistic compare-and-swap, and the two are different answers to the same question ("how do we stop staff from clobbering each other's edits"), not complementary mechanisms — building both would leave two ways to reason about the same problem, and no clear owner for which one a given Job field falls under next time a new field is added.

We're replacing the per-field CAS mechanism outright with pessimistic, whole-Job record locking (issue #34):

- Opening a Job for edit (clicking "Edit" in the Jobs list) acquires an exclusive lock on the entire record via an atomic conditional `UPDATE` — the same compare-and-swap *pattern* the old code used per field, just applied once, to the lock itself, since acquiring a lock has exactly the same "two people race for it" race condition a field update did.
- The lock covers every field, including Discrepancy Flag and Close-Out, which move from one-click table toggles into the same locked detail view as everything else — there's no longer a quick-toggle path that bypasses the lock.
- A lock auto-expires after 15 minutes of inactivity, checked lazily at acquire time (`locked_at < now() - interval '15 minutes'` counts as unlocked) rather than via a background job, so an abandoned edit (browser closed, staff member walked away) doesn't permanently block the Job.
- Saving applies every changed field in one combined `UPDATE` and releases the lock in the same call; canceling releases the lock without saving. The detail page re-verifies on load that the current session still holds the lock — it may have expired, or been raced, between acquiring it and the page rendering — rather than trusting a successful redirect to still imply a valid lock.
- The Jobs list shows a lock-status badge (who holds it, if anyone with a currently-active lock) so staff aren't surprised when "Edit" fails.

This is a straight reversal, not an addition: `casUpdateJobField`, `FieldConflictError`, and all ten per-field `updateJobX` functions are removed, along with the dashboard's per-field inline-edit forms and the `edit-field.ts` extraction built on top of them (issue #24). Two Jobs schema columns replace the removed mechanism's implicit "current value is the version" check: `locked_by_user_id` (nullable, FK to `users`) and `locked_at` (nullable timestamp).

We considered keeping CAS for low-traffic fields and adding locking only for the higher-contention ones (Discrepancy Flag, Close-Out), but rejected a mixed model — it reintroduces exactly the "which mechanism applies to this field" cognitive load the simpler whole-Job model is meant to remove, for a marginal win that doesn't matter at this team's Job-edit volume.
